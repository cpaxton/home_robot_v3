## Self-occluding workspace: confirmed, still an execution blocker

The [blocking review](https://github.com/cpaxton/home_robot_v3/pull/226#discussion_r4417132335)
is correct. A new regression raycasts a MuJoCo robot and wall into a calibrated
depth image, constructs the actual `ObservedWorkspace`, and checks the real native
collision/planning interface. Robot surfaces are occupied; their interiors are
unknown. Even oracle-perfect robot endpoint exclusion leaves those cells unknown
and preserves the wall. Both maps reject the starting configuration with
`robot_scene_collision` / `invalid_start`.

This regression documents a limitation; it does not fix it by declaring unknown
space free. The synthetic public-tool transfer/swap fixture uses an all-free
predicate and validates orchestration only. The API, paper, PR description and
[execution plan](../plans/2026-10-26_observed_native_execution.md) now state the
limitation explicitly. Improving wrist/head visibility does not solve this
independent planning problem. A full observed executor is not merge-ready on this
evidence; the independently reviewable contract/diagnostic foundation is the
current scope.

## Transport timeout boundary: retain conservative possible-dispatch semantics

The [suggested return-time marker](https://github.com/cpaxton/home_robot_v3/pull/226#discussion_r4417133746)
would be unsafe for an ordinary timeout: transport can send a command, cause
actuation, and then lose the acknowledgement. Marking only on return would claim
no actuation in that case. The existing boundary is retained and documented:
`execution_started=true` means possible dispatch/progress, not confirmed motion.
Without an explicit transport no-send receipt, an exception after transport entry
cannot certify no actuation.

Six integration regressions exercise joint/open/close transport, each with a
timeout before or after the mocked side effect. All return a partial
`command_outcome_unknown` receipt, with no completed operation or private error
details leaked. Existing observation/preflight timeout tests still prove no
actuation when transport was never entered. No new transport acknowledgement
semantics are inferred.

## Shared geometric uncertainty margin

The [margin consistency comment](https://github.com/cpaxton/home_robot_v3/pull/226#discussion_r4417138927)
is addressed by one `pose_uncertainty_margin` helper, used by payload planning,
visual bounds and gripper envelopes. It saturates angular displacement at pi.
Independent rigid-point perturbation tests cover zero, small, quarter-turn,
half-turn and greater-than-pi error bounds. Admitted current inputs remain below
their original bounds, so this does not change the recorded control outcomes or
relax evidence admission.

## Actual Stretch render/calibration invariants

The [intrinsic-consistency request](https://github.com/cpaxton/home_robot_v3/pull/226#discussion_r4417139875)
is covered at 424×240 and 848×480 using the packaged Stretch model and actual
camera-parameter setup. Tests exercise registration and the real server
constructor's `head_K`, stubbing only external sockets/process startup. MuJoCo's
GL-camera frustum supplies an independent focal-length reference without opening
a GPU context. Tests check projected rays through clockwise image rotation,
optical-baseline depth offset and unfilled registration holes.

The first test attempt incorrectly expected exactly unchanged depth under the
head baseline. The model's approximate Euler angles introduce a small axial
component (about 12 micrometres in this fixture); the corrected assertion derives
that component independently from world camera FK instead of loosening tolerance
or changing registration. Simulator teardown is stubbed alongside startup.

The [focal-length change](https://github.com/cpaxton/home_robot_v3/pull/226#discussion_r4417140898)
is intentional: 42° pinhole FOV yields 312.6107 px at 424×240, versus the previous
physical calibration 304.24/304.07 px. The API now documents this roughly 2.7%
simulator metric-geometry change, pixel-center convention, unchanged hardware
settings and the need to rerun/version historical comparisons. This follow-up
does not alter either calibration; it pins and explains the PR's existing change.
