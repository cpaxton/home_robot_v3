\section{Method}
\label{sec:method}

Dynagraph is implemented as \texttt{DynagraphController}, a thin extension of \texttt{GraphEQAController}, which itself subclasses the DynaMem navigation agent.
The design principle is \textbf{one perception step, two memory writes, one maintenance pass}: first the voxel map (unchanged DynaMem rules), then graph unification (GraphEQA), then Dynagraph-specific graph maintenance.

\subsection{System overview}

At each control step the robot receives RGB-D observations and pose from a MuJoCo ZMQ server (or Habitat bridge, when available).
The controller calls the inherited DynaMem \texttt{update()}, which appends the frame and fuses it into \texttt{SparseVoxelMap} using the same add/remove and exploration logic as manipulation-oriented DynaMem runs.
Immediately afterward, \texttt{update\_graph\_memory\_from\_dynamem\_observation} reads the freshly updated map and observation log to add or reinforce graph nodes.
\texttt{DynagraphController} then calls \texttt{maintain(obs\_count)} for staleness pruning.

Per control step the pipeline is:
\begin{enumerate}
  \item \textbf{Voxel write (DynaMem, unchanged).} Fuse the new RGB-D frame into \texttt{SparseVoxelMap}; append the frame to the observation log; refresh per-voxel provenance (\texttt{last\_seen}, supporting \texttt{obs\_id}).
  \item \textbf{Graph write (GraphEQA).} The shared hook lifts object hypotheses from the updated map and current frame (instance masks, voxel semantics, or sensor VLM) into \texttt{GraphEQAMemory}, tagging each node with its supporting \texttt{obs\_id} and the current controller step.
  \item \textbf{Graph maintenance (Dynagraph).} Apply spatial merge (Section~\ref{sec:spatial_merge}) and staleness pruning (Section~\ref{sec:staleness_pruning}) so the graph stays compact and aligned with the voxel substrate.
\end{enumerate}
All three stages run on the same observation log, so navigation, exploration, and EQA read from one evidence trail.

\subsection{Stage 1: DynaMem voxel update (unchanged)}

We deliberately reuse DynaMem's voxel fusion rather than maintaining a parallel map for EQA.
The voxel map is an obstacle grid for A* planning and value-based exploration, but also a semantic index: each voxel accumulates vision-language features and records \textbf{provenance}---which observation index last wrote to it, and (in the 2D projection) a \textbf{recency field} over when voxels were last refreshed.
Observations live in an append-only \textbf{frame log}; each frame bundles RGB-D, intrinsics, extrinsics, robot base pose, and optional instance segmentation.
Dynamic scenes are handled by the same DynaMem rules that add geometry when objects appear and retire voxels when support disappears.

\subsection{Stage 2: GraphEQA unification (extra steps)}

Graph construction is \emph{not} a separate perception pipeline.
After Stage~1, the shared hook inspects the latest frame and voxel semantics, optionally runs instance detection or a sensor VLM (\texttt{SensorGraphBuilder}), and writes object hypotheses into \texttt{GraphEQAMemory} with the \texttt{obs\_id} and \texttt{last\_seen} step from the current controller tick.
Navigation-only samples (e.g.\ generic ``object'' fallbacks) can be recorded without spawning graph nodes, matching GraphEQA's separation of exploration views from semantic hypotheses.

\subsection{Voxel-grounded scene graph}

The scene graph is derived from the DynaMem substrate on every step rather than maintained independently.
Each node is an object or region with labels, a world-space position, an \texttt{obs\_id} pointing into the frame log, and a discrete \texttt{last\_seen} step aligned with the controller clock.
Edges encode spatial relations (\emph{near}, \emph{on}, \emph{on\_floor}).
When a new detection reinforces an existing object, merge rules update the node's position, labels, and \texttt{last\_seen}; the supporting \texttt{obs\_id} tracks the freshest evidence.

\textbf{Disappearance.} An object is considered gone when its voxel support stops being refreshed and no new observation reinforces it within the staleness horizon.
Concretely, voxel fusion writes to a voxel only while the sensor observes it; when a voxel stops being refreshed, the map can remove its geometry, and the graph node that depended on that support ceases to be reinforced ($t_n$ is not updated).
The staleness rule of Section~\ref{sec:staleness_pruning} then retires the node (with its linked observations) from the graph presented to the VLM, so EQA is not misled by hypotheses the map no longer supports.

An EQA module queries a shared VLM with the serialized graph and task-relevant images until confidence is sufficient or further exploration is requested.

\subsection{Stage 3: Dynagraph graph lifecycle}

On top of GraphEQA node creation, Dynagraph adds merge and staleness (below).
Labels in Stage~2 come from instance segmentation (optional YOLO-E) and/or VLM scene descriptions.
Each new detection creates a graph node and observation unless \textbf{spatial merge} applies.

\subsection{Spatial merge}
\label{sec:spatial_merge}

If \texttt{dynagraph\_merge\_xy\_m} $> 0$ (default 0.45\,m), a new detection whose primary label matches an existing node and whose XY distance is within the threshold \emph{updates} that node: running-mean XYZ, increased support count, refreshed \texttt{last\_seen}, and merged label set.
This reduces duplicate nodes when the robot revisits the same object from a new viewpoint.

Formally, for a candidate node $c$ with primary label $\ell(c)$, XY position $\mathbf{p}_c$, and a stored node $n$ with $\ell(n)=\ell(c)$, the merge fires when $\lVert \mathbf{p}_c - \mathbf{p}_n \rVert_2 \le \rho$ (merge radius, default $0.45$\,m) and replaces $n$ by
\begin{equation}
  \mathbf{p}_n \leftarrow \tfrac{w_n}{w_n+1}\,\mathbf{p}_n + \tfrac{1}{w_n+1}\,\mathbf{p}_c, \qquad
  w_n \leftarrow w_n + 1, \qquad
  t_n \leftarrow t_c,
\end{equation}
where $w_n$ is the support count and $t_n$ is the node's \texttt{last\_seen} step.
Otherwise the candidate spawns a new node and observation.

\subsection{Staleness pruning}
\label{sec:staleness_pruning}

If \texttt{dynagraph\_staleness\_horizon} $> 0$ (default 256 controller steps), \texttt{maintain(current\_step)} removes nodes whose \texttt{last\_seen} is older than the horizon, deletes their observations, renumbers nodes, and rebuilds edges.
This discards objects that are no longer visible or relevant---analogous in spirit to map pruning in dynamic memory systems, but on the discrete object graph used for EQA.

Formally, at step $t$ every node $n$ with
\begin{equation}
  t - t_n > \tau \quad (\tau = \text{staleness horizon, default } 256)
\end{equation}
is pruned together with its linked observations; the surviving nodes are renumbered and edges rebuilt so the serialized graph the VLM sees contains only hypotheses the voxel map still supports.

\subsection{Exploration and EQA loop}
\label{sec:eqa_loops}

After map and graph updates, Dynagraph answers questions with one of two controllers that share the same memory substrate.
Dynagraph-specific Rerun logging exposes \texttt{world/dynagraph/} for graph inspection during development.

\paragraph{Classic planning loop.}
The default path inherits GraphEQA-style iteration: optional rotation-in-place scan, navigate toward frontiers or graph-guided Image-$N$ waypoints, call \texttt{query\_answer} (graph + task-relevant RGB) for a letter/confidence, and repeat until confident or the planning budget is exhausted.
Each iteration is a monolithic VLM call that jointly decides whether to answer or where to go next; there is no explicit verify gate before committing an answer.

\paragraph{Agentic tool loop.}
Optionally (\texttt{eqa.agentic\_verify} / \texttt{EMET\_EQA\_AGENTIC\_VERIFY}), \texttt{run\_eqa} switches to a bounded tool-calling loop (\texttt{AgenticEQAExecutor}).
A fixed system prompt lists a small tool set; each round the model emits JSON tool calls, the controller executes them (navigation updates map/graph automatically), and a compact state message summarizes remaining budget plus \emph{evidence cards} for candidate places so the agent does not re-pick failed locations.
Cheap open-vocab detectors (SigLIP / OWLv2 / YoloE) act only as \textbf{high-recall proposals} in state; answerability and the final letter are \textbf{VLM-first} (\texttt{vlm\_assess} on a fresh RGB, then \texttt{submit\_answer}).
An optional text-only \textbf{router} VLM proposes tool calls among recalled cards; with the router off, a deterministic heuristic walks the same recalled list (used in our Habitat H2H of record for speed and stability).
Full tool schemas and response format live in Appendix~\ref{app:agentic_tools}.

\paragraph{Hypothesis recall (not a second policy).}
\texttt{inspect\_graph} / post-capture refresh retrieves up to $K$ place cards (\texttt{EMET\_EQA\_HYP\_RECALL\_K}, default 6) from graph label hits, SigLIP hits, and frontier waypoints.
Retrieval uses a short source-tier + keyword/landmark key with planar distance as a weak tiebreak and packs diversified top-$K$ (graph and frontier when both exist); an internal rank key may order fallback walks but is \textbf{not} shown to the router as a utility score.
Each card is evidence: \texttt{obs\_id}, phrase, source, $xyz$, optional labels / raw SigLIP similarity, plus tried / nav-visit marks.
Visited \textbf{frontier} nodes are retired from the graph (they are no longer frontiers) so they cannot reappear as candidates.

\paragraph{Tools (summary).}
In answer mode the agent may call: \texttt{inspect\_graph} (refresh evidence cards), \texttt{explore\_frontier} (grow coverage; agentic prefers a VLM pick among a small pool of reachable frontier RGBs, else uncovered / graph heuristics), \texttt{navigate\_to\_obs} (go to a listed \texttt{obs\_id}), \texttt{look\_around} (in-place scan), \texttt{verify\_siglip} (PRESENT / CANDIDATE / ABSENT proposal with similarity), and \texttt{submit\_answer} (MCQ letter; unlocked when VLM assess says answerable, not by detector PRESENT alone).
Explore-only mode replaces \texttt{submit\_answer} with \texttt{finish}.
These EQA tools are distinct from the interactive Discord/chat agent tools in Section~\ref{sec:interactive_agent}.

\textbf{Habitat EQA grounding (HM-EQA).}
On the Habitat harness we add three inference-time mechanisms on top of either loop:
(1)~\textbf{navmesh navigation} with Habitat compass/yaw conventions and frontier re-picking when goals stall;
(2)~\textbf{phrase-level CONFIRMED\_MEMORY}---multi-word question phrases (e.g.\ ``woven basket'') drive SigLIP alignment and coverage gates instead of fragmented stopword tokens, with the SigLIP encoder retained through voxel VRAM release before EQA;
(3)~\textbf{location multiple-choice prompts} for visibility+where questions (``Did you see \ldots\ anywhere?'') that instruct the VLM to pick a place letter (A--D) using graph memory even when the object is absent from attached images, plus a letter-only salvage pass when the model answers yes/no instead.
The HM-EQA paper rows pin the \emph{standalone} confirmed-memory block (\texttt{merged\_memory: false}); the product default merges it into the scene-graph serialization, and the image-description lines omit labels already tagged on graph nodes.
MCQ choice-rotation debiasing runs at episode end for Dynagraph only (classic path; typically off in tuned HM-EQA profiles).

\subsection{Simulation ground-truth supervision}
\label{sec:gt_supervision}

For MuJoCo simulators (\texttt{emet serve mujoco}, Robocasa, MolmoSpaces), the ZMQ server attaches \texttt{sim\_object\_placements} to \texttt{emet\_session}: per-body semantic \texttt{cat}, world \texttt{pos}, and axis-aligned \texttt{bounds} from MuJoCo geoms (Appendix~\ref{app:ground_truth_graph}).
\texttt{emet run dynagraph --ground-truth} loads graph nodes from this metadata instead of VLM or YOLO-E hypotheses, while \textbf{Stage~1 voxel fusion is unchanged}: rotate-in-place, frontier exploration, and RGB-D frame logging proceed as in the standard stack.

Two CLI modes support evaluation.
\textbf{Ground-truth mode} (\texttt{--ground-truth}) uses sim labels as the authoritative graph; GT nodes are exempt from staleness pruning and perception hooks do not append duplicate object nodes, but each control step records a navigation viewpoint sample (camera pose and RGB) for the exploration trail.
\textbf{Compare mode} (\texttt{--compare-to-gt}) runs the full perception graph and overlays a reference GT layer in Rerun for alignment reports.
Bidirectional \textbf{association} links sim GT to sensor evidence: YOLO-E instance centroids match nearest GT bodies in XY (forward), and projected GT bounding boxes match instance masks in each frame (reverse), producing per-frame association records for metrics and dataset export.

Episode export (\texttt{--ground-truth --export}) writes the common \texttt{MemoryState} directory layout: graph, frame log (RGB-D, poses, instances), \texttt{sim\_object\_placements.json}, and GT association sidecars---used for object-finding benchmarks (Section~\ref{sec:gt_experiments}) and future VLM fine-tuning.

\subsection{Implementation}

Entry point: \texttt{emet run dynagraph} (\texttt{run\_dynagraph.py}, \texttt{DynagraphController}).
Configuration: \texttt{dynav\_config.yaml} plus CLI overrides \texttt{--merge-xy-m} and \texttt{--staleness-horizon}.

\subsection{Interactive agent front-end}
\label{sec:interactive_agent}

The same Dynagraph stack is the default memory backend for the interactive tool agent (\texttt{emet run agent --memory-backend dynagraph}).
Natural-language turns are routed by a lightweight text LLM into \emph{chat} tools that call the controller: \texttt{explore} / \texttt{scan\_environment} for coverage, \texttt{find\_objects} for open-vocab localization, \texttt{describe\_scene} / \texttt{send\_image} / \texttt{send\_map\_snapshot} for sharing views and maps, and \texttt{query\_memory} for graph/voxel QA (optional \texttt{--eqa} for VL captions).
Discord and the terminal share one input queue; action status is announced while long motions run.
Scored Habitat HM-EQA uses the same episode function as \texttt{emet-habitat} via \texttt{emet run agent --eqa-eval} (optional \texttt{--extra-instruction}).
The Discord/chat tool-router is not on the scored path; when agentic verify is enabled, scoring uses the EQA tool loop of Section~\ref{sec:eqa_loops} instead.
This front-end does not change Dynagraph update rules---it exposes the same memory used by Habitat and MuJoCo paper harnesses for live debugging, demos, and eval.
