\section{Multi-room agent-task preflight}
\label{app:agent_task_preflight}

We introduce three small multi-room cases for validating the agent interface and
evaluation machinery before larger experiments: cross-room delivery, two-object
collection, and a moved-object revisit. A deterministic three-room MuJoCo fixture
uses the packaged rby1 geometry, open placement trays, and a fixed scene seed.
Success requires each target's measured center to lie within its specified XYZ
placement region and the object not to be held. Negative controls include no
action, incorrect destinations, partial completion, and stale plans.

The initial controls invoke the existing CHAT planning/execution tool registry
with ground-truth object geometry, synthetic grasps, footprint-checked kinematic
navigation, and object-pose teleportation. Rendering uses forward kinematics and
a recorded fixture-only downward head-camera mount. These controls establish
repeatable assisted execution and evaluator behavior; they do not establish
contact-stable manipulation, learned perception, agent planning, or memory
recovery. The moved-object witness has privileged knowledge of the relocation.
Multi-room live ZMQ and full learned-memory integration are separate acceptance gates.

Recorded events separate policy-visible state from private evaluator truth and
link tool outcomes, observations, trajectories, and goal predicates. Offline
exports produce synchronized replay, video, and figures from the same evidence.
Absent learned memory is explicitly marked as unrecorded rather than reconstructed
from ground truth. The initial release makes no paid model calls.

\subsection{Local-policy task interface}
The next preflight stage runs a cached local language model through the shared
agent's bounded task mode, also exposed by \texttt{run\_agent.py}. This mode
preserves conversation history across decisions and continues after tool results.
The environment provides bounded camera-based room search, navigation, and either
combined pick-and-place or separate plan/execution calls. All manipulation still
uses the shared guarded planning and execution implementation with the assistance
profile described above.

Three layouts are available: the original three-room fixture, a three-room layout
with extra furniture, and a four-room layout including a study. Object recognition
is assisted: labels and positions enter the observation cache only when the
corresponding object has pixels in the rendered head-camera segmentation. Hidden
world changes leave cached observations unchanged until a later observation.
This cache is not the learned voxel/semantic-graph backend. Policy prompts,
responses, syntax repairs, command outcomes and historical cache contents are
recorded separately from evaluator truth.

\subsection{Visual fixtures and question-answering preflight}
A second visual profile adds recognizable procedural furnishings: appliances and
cabinets in the kitchen, a sofa in the living room, bookshelves in the study, and
chairs in the dining room. Task receptacles have visible rims, the green object
is named a cube to match its geometry, and placement returns the robot to a
room-center observation pose. RGB observations are recorded at $960\times540$.
These are still assisted procedural fixtures, not native household datasets.

Ten question types cover attributes, counting, image-relative spatial relations,
occupancy, room appearance, named-room recall, multi-view inventory, temporal
change, placement verification, and insufficient evidence. The initial QA mode
supplies fixed views; it does not evaluate active exploration. Only named-room
recall receives explicit room metadata. Temporal and placement images use staged
state changes. Each answer must follow its declared schema and cite its supplied
view IDs; correctness and evidence completeness are scored separately. Correct
citations alone do not prove that a model inspected the image.

A QA pack is rejected if any required target has fewer than 128 segmentation
pixels, a bounding-box dimension below eight pixels, or touches an image boundary.
Public image/question files are separated from private answer keys and evaluator
state. The local QA runner sends RGB through the shared bounded task agent, using
view-advance and answer-submission tools. Every question starts fresh model
history. Image hashes and model input events record the supplied evidence.

All three layouts passed these readability checks and positive/negative scorer
controls; all nine action task/layout controls remained solvable under the new
profile. Controls do not establish learned QA accuracy. One cached Qwen3.5-0.8B RGB
run passed 6/10 questions: color, counting, relative position, empty-tray occupancy,
kitchen identification, and abstention. Multi-view inventory and room recall
produced no accepted answers; temporal direction was correct but lacked a required
citation, and placement verification was incorrect. This is a development
diagnostic after a recorded tool-array syntax repair, not a general accuracy estimate.
Earlier policy results
above used the earlier visual profile and should not be pooled with this one.

\subsection{Queued CUDA action rollouts}
A separate, sequential Qwen2.5-3B-Instruct CUDA batch used the second visual profile
and a fixed source snapshot. Each episode had a 16-decision limit, 128 generated
tokens per call, and a 300-second deadline. All three workers completed with full
visual evidence, but no episode passed the complete task contract. Delivery
claimed completion without manipulation; collection delivered one requested object
but selected the green cube for other placements. Revisit recovered the relocated
cylinder and passed both final placement and temporal predicates, but continued
acting until its decision budget expired. This distinguishes a usable benchmark
integration from reliable agent completion. These are visible-label text-policy
runs with assisted skills, separate from the RGB QA results above. The earlier CPU
runs differ in code and scene profile and are not a controlled device comparison.
