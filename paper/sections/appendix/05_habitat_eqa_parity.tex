\section{Habitat HM-EQA harness vs.\ GraphEQA}
\label{app:habitat_eqa_parity}

This appendix records how the \texttt{emet} Habitat EQA harness (\texttt{feature/habitat-eqa-harness}) compares to the reference GraphEQA Habitat stack~\citep{saxena2024grapheqa}, what is intentionally different, and interim accuracy on our development machine.
The harness drives \texttt{GraphEQAMemory} / \texttt{DynagraphController} inside Habitat-Sim rather than ROS + Hydra; HM-EQA uses 113 multiple-choice questions (Explore-EQA indices 0--112) with scene init poses from the public CSVs.

\noindent\textbf{Reference setup.}
GraphEQA Habitat sim uses \texttt{use\_semantic\_data: True}: ground-truth HM3D-Semantics instance masks (not Detic) feed Hydra 3DSGs; a TSDF frontier planner with task-relevant frontier enrichment; camera 120$^\circ$ HFOV at 1.5\,m height and $-30^\circ$ tilt (640$\times$480); up to 20 VLM planning iterations; and API VLMs (GPT-4o, Gemini, etc.).
Detic segmentation is used in real-world experiments only.

\subsection{Semantics and frontier gaps (detail)}

\textbf{Ground-truth semantics.}
When GraphEQA sets \texttt{use\_semantic\_data: True}, every HM-EQA episode is assumed to have HM3D semantic annotations.
Our harness enables the Habitat semantic sensor when \texttt{.semantic.glb} is present for the scene; on a typical cache with train semantics partially downloaded, \textbf{37/113} paper questions and \textbf{14/49} unique paper scenes had semantic assets at the time of writing---the remainder fall back to depth voxel mapping and VLM (or keyword) graph labels.

\textbf{Frontier planning (fluid map vs.\ graph nodes).}
Both DynaMem and GraphEQA share the same \emph{fluid} 2D frontier: reachable free-space edges on the voxel grid (\texttt{get\_outside\_frontier}), minus explored cells.
\texttt{SparseVoxelMapNavigationSpace.sample\_exploration} picks a grid cell using a time-since-visit heuristic and, when \texttt{keyword\_score\_weight}$>0$, a question-keyword overlap map (\texttt{keyword\_score\_map})---no discrete graph required.

\textbf{Frontier v2 (optional, default in \texttt{dynav\_config.yaml}).}
When \texttt{graph\_eqa\_frontier\_nodes.enabled} is true, \texttt{sync\_frontier\_nodes} clusters the same unexplored mask into up to 12 \texttt{GraphEQAMemory} nodes (\texttt{is\_frontier=True}), exposes them in EQA \texttt{IMAGE\_DESCRIPTIONS}, and routes low-confidence iterations via \texttt{\_best\_frontier\_point\_from\_graph} before falling back to fluid \texttt{sample\_frontier}.
HM-EQA CLI flags \texttt{--frontier-nodes}/\texttt{--no-frontier-nodes} and \texttt{--frontier-keyword-weight} select ablation arms (script \texttt{run\_habitat\_frontier\_ablation.sh}).

\textbf{Paper-reproduction baseline.}
Closest to upstream GraphEQA fluid exploration (no graph frontier nodes): \texttt{--no-frontier-nodes --frontier-keyword-weight 0}.
Earlier \texttt{emet} batches that left frontier nodes enabled are \emph{frontier v2}, not a strict paper clone.

Reference GraphEQA still uses a separate TSDF map and VLM \texttt{enrich\_frontiers} prompts; full parity on exploration policy remains future work.
A navigation fix (2026-06) maps VLM \texttt{action: Image $N$} through the attached \texttt{obs\_ids} order rather than the full observation list index.

\noindent\textbf{Takeaway.}
Official GraphEQA on HM-EQA is \textbf{63.5\%} (GPT-4o) to \textbf{67.0\%} (Gemini-2.5Pro).
Our harness reaches \textbf{$\sim$40--50\%} on small slices with local 3--4B VLMs---below API baselines but competitive with our reproduced gemma-3-4b paper batch---consistent with weaker VLMs and partial GT semantics, not broken grading (mock GraphEQA vs.\ Dynagraph match at 100\% on Q0--5).
Frontier v2 (graph nodes on) underperformed the paper repro on Q0--19 (\textbf{25\%} vs.\ \textbf{40\%}); the ablation table isolates fluid vs.\ node-guided exploration after fixing VLM \texttt{action} $\rightarrow$ navigation index alignment.
